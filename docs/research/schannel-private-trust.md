# P-12: Schannel private trust and no-install local TLS fixtures

**Evidence retrieved: 2026-11-04.** Scope: native Windows Schannel client design, explicit private CA trust, and future loopback-only tests without installing roots. This is source-based research, **not implementation, executed TLS testing, or qualification of Windows native trust**. Only public Microsoft documentation and maintained curl Schannel source were used as external evidence. Context7 was checked first; agent-reach Exa reached its rate limit, so Microsoft pages were read through its Jina route. curl source was read using the agent-reach GitHub CLI route.

No TLS test connection, pool connection, application protocol exchange, hardware operation, certificate-store write, root installation, user/VM creation, or machine-policy change was performed. Documentation retrieval is not a pool probe. No personal certificates, configuration, device information, or local paths are reproduced here.

## 1. Decision and relationship to the existing research

Keep [secure-transport-backends.md](secure-transport-backends.md), sections 3 and 4, as the **normal-mode baseline**: outbound `SCH_CREDENTIALS` with `SCH_CRED_AUTO_CRED_VALIDATION | SCH_CRED_NO_DEFAULT_CREDS`, configured reference name supplied to `InitializeSecurityContextW`, and no `SCH_CRED_MANUAL_CRED_VALIDATION`, `ISC_REQ_MANUAL_CRED_VALIDATION`, or `SCH_CRED_NO_SERVERNAME_CHECK`. For the strict revocation contract investigated here, additionally request `SCH_CRED_REVOCATION_CHECK_CHAIN_EXCLUDE_ROOT`; do not set either revocation-ignore credential flag. Automatic validation and suppression of automatic client identity are separate controls.[^credentials][^isc]

**Confirmed independently:** `SCH_CREDENTIALS.hRootStore` is **server-only**, for servers authenticating clients. It is not a client custom-CA input. Putting a fixture root there does not establish private client trust.[^credentials]

There is a narrowly justified alternative for an **explicit, endpoint-scoped custom-CA mode**: Schannel performs TLS, while the application invokes Windows certificate-chain and SSL-policy APIs against an exclusive in-memory anchor set. Microsoft documents manual validation and its obligations; curl corroborates the memory-store/exclusive-engine mechanism. This is not an always-accept callback or an insecure test switch. Nevertheless, it is an exception to the earlier note's blanket production prohibition on manual validation, **not a silent reinterpretation of that recommendation**. Do not make all clients manual merely to simplify fixtures.[^manual][^engine][^curl-verify]

**Recommendation:** retain normal automatic native trust; investigate custom trust only as a distinct policy path with the complete acceptance gate below. Until equivalent applicable OS checks, IP identity behavior, revocation inputs, and blocking behavior are qualified on the supported Windows baseline, keep production custom-CA support unavailable and confine experiments to the explicit test path. If those obligations cannot be met, report unsupported custom trust rather than weakening normal trust. A successful private-store test does not qualify automatic Windows-root validation.

## 2. The trust-engine distinction that matters

* `hRestrictedRoot` narrows the existing root store to a **proper subset of its certificates**. It is not the documented mechanism for introducing an uninstalled private root.
* `hExclusiveRoot` supplies application-specific trust anchors. A valid exclusive-root or exclusive-TrustedPeople store enables exclusive trust: the system **Root and TrustedPeople stores are ignored as trust sources**. This replaces anchors; it does not merely append private roots to ordinary Windows roots.
* `hRestrictedOther` restricts supporting certificate/CRL stores searched; `hRestrictedTrust` restricts CTL search. `rghAdditionalStore` and `CertGetCertificateChain.hAdditionalStore` provide supporting objects, **not automatic trust anchors**. Restricting anchors is not the same as eliminating all OS store/cache access.
* **Follow-on SDK/execution correction (2026-11-04):** the Microsoft SDK explicitly makes both exclusive handles mutually exclusive with **all three restricted handles**. An engine combining `hExclusiveRoot` with `hRestrictedOther`/`hRestrictedTrust` was rejected with `E_INVALIDARG` in the subsequent offline fixture. All restricted handles must remain NULL; supply supporting certificates/CRLs through additional stores instead. The SDK's exclusive-mode `hWorld` can still include the system CA/My supporting stores. Exclusive anchors are not a hermetic certificate-store sandbox, and this mechanism does not select/use a private client key.[^sdk-header]
* Keep `hExclusiveTrustedPeople = NULL` and do not request `CERT_CHAIN_ENABLE_PEER_TRUST`. Peer trust has materially different chain-building semantics.
* Keep `dwExclusiveFlags = 0`. `CERT_CHAIN_EXCLUSIVE_ENABLE_CA_FLAG` deliberately permits a **non-self-signed intermediate** to terminate the chain as an anchor, with no signature verification or revocation check on that anchor. That is a separate partial-chain trust policy, not required for a private self-signed root.[^engine][^getchain]

Exclusive roots are supported from Windows 7; the exclusive-CA flag from Windows 8. Those dates do not relax the project's modern `SCH_CREDENTIALS` API baseline, Windows 10 1809 or later, or constitute a supported-OS product promise.[^engine][^credentials]

## 3. Required explicit-custom-CA acceptance procedure

The following is a proposed security contract, not drop-in implementation code. Every allocation, parse, SSPI call, chain call, and policy call must be checked. Failure at any point prevents `VerifiedOpen`; no security failure enables plaintext fallback.

1. **Freeze policy before connecting.** Capture the configured DNS name or literal IP, trust-mode identifier, immutable CA bytes, revocation/network policy, and one absolute deadline. Reject malformed/empty/unreadable CA input rather than falling back to system trust. Keep CA selection endpoint-scoped; never infer anchors from the certificate received on the wire. Use separate credential/cache ownership across normal/custom trust and across trust-policy revisions; the Schannel session cache depends in part on target name and credential handle. Revalidate on every connection, including resumption; unavailable peer evidence is a failure, not an exemption.[^credentials][^isc]

2. **Build an isolated anchor store.** Use `CertOpenStore(CERT_STORE_PROV_MEMORY, ..., CERT_STORE_CREATE_NEW_FLAG, ...)`, decode bounded public certificate input, and add only the explicitly approved self-signed root CA certificates. Validate the intended CA/basic-constraints/key-usage role; do not promote every certificate in a mixed bundle to an anchor. Memory stores start empty and are not automatically persisted. Never open `Root`, `CA`, `My`, or `TrustedPeople` for writing, call a system-store add API, save this store, or enable file/registry commit behavior. Keep supplied intermediates and fixture CRLs in a separate supporting memory store.[^open][^add][^engine]

3. **Create a nondefault, exclusive chain engine.** Zero-initialize the SDK-sized `CERT_CHAIN_ENGINE_CONFIG`, set `cbSize`, set `hExclusiveRoot` to the nonempty anchor store, and leave **all three restricted handles**, `hExclusiveTrustedPeople`, and `dwExclusiveFlags` zero. The original proposal to combine exclusive roots with restricted supporting/CTL stores was invalid; the SDK and follow-on fixture establish their mutual exclusion. Supply reviewed supporting certificates/CRLs via additional memory stores, without treating them as anchors. This does not isolate all native OS supporting stores/caches or prove production equivalence with distrust/enterprise policy. `CertCreateCertificateChainEngine` failure is fatal; never substitute `NULL`/`HCCE_CURRENT_USER`, because `NULL` to `CertGetCertificateChain` selects the default engine. Exclusive trust alone does not disable URL retrieval; see section 6.[^engine][^create][^getchain][^sdk-header]

4. **Replace Schannel's automatic peer-certificate decision only in this mode.** Acquire outbound credentials with `SCH_CRED_MANUAL_CRED_VALIDATION | SCH_CRED_NO_DEFAULT_CREDS`, no client certificate (`cCreds = 0`, `paCred = NULL`), and the same TLS protocol/cipher restrictions as normal mode. Do not set `SCH_CRED_NO_SERVERNAME_CHECK`, enable early application data, or regard manual-mode `SEC_E_OK` as authenticated success. Continue passing the configured reference to SSPI, but do not rely on automatic name validation in manual mode: step 8 supplies the independent name-policy gate. Keep application plaintext writes **and delivery of peer application plaintext** gated until independent verification succeeds and required handshake output is flushed.[^credentials][^manual][^isc]

5. **Obtain the actual peer leaf and intermediates.** After the handshake permits querying it, call `QueryContextAttributesW(SECPKG_ATTR_REMOTE_CERT_CONTEXT)` and require a successful, non-null `PCCERT_CONTEXT`. Its `hCertStore` supplies received intermediates; ordering does not prove chaining and none of those objects becomes trusted merely by being received. Keep the context alive throughout chain construction/policy checks. Use its store as additional supporting input, or copy supporting certificates into the bounded auxiliary memory store when combining fixture CRLs.[^query][^manual]

6. **Build and check the chain with server usage and revocation.** Zero-initialize `CERT_CHAIN_PARA`, set its size, and set `RequestedUsage` to `USAGE_MATCH_TYPE_AND` with exactly `szOID_PKIX_KP_SERVER_AUTH`. Call `CertGetCertificateChain` with the nondefault engine, actual peer leaf, current time (`pTime = NULL` in production), supporting store, and **`CERT_CHAIN_REVOCATION_CHECK_CHAIN_EXCLUDE_ROOT`**. Do not confuse this flag with similarly named `SCH_CRED_*` flags. Request explicit strong-signature checking through `pStrongSignPara` under a reviewed OS-compatible policy; do not disable the end-key check. The SDK documents extra-field declarations through `CERT_CHAIN_PARA_HAS_EXTRA_FIELDS`; use the declared structure/size, not copied compatibility layouts. `CERT_CHAIN_OPT_IN_WEAK_SIGNATURE` is an additional documented weak-signature control, not proof of full Schannel-policy equivalence.[^getchain][^chainpara][^strong]

7. **Treat successful chain construction as data, not acceptance.** Require a non-null, structurally usable returned chain and inspect its aggregate `TrustStatus.dwErrorStatus`; for diagnostics also inspect simple-chain/element statuses. Proposed strict acceptance is **`dwErrorStatus == CERT_TRUST_NO_ERROR`**, not a small allowlist of rejected bits or only `rgpChain[0]`. Do not test `dwInfoStatus == 0`: self-signed/exclusive-store informational bits can be expected. Fatal errors include untrusted root, partial chain, invalid signature/time/usage/basic or name constraints, unsupported critical extension, explicit distrust, weak signature, revoked certificate, **`CERT_TRUST_REVOCATION_STATUS_UNKNOWN`**, and **`CERT_TRUST_IS_OFFLINE_REVOCATION`**. New/unrecognized error bits also fail closed. Do not clear bits to make a fixture pass.[^getchain][^trust]

8. **Apply Windows SSL server policy to that same chain.** Set `SSL_EXTRA_CERT_CHAIN_POLICY_PARA` (documented also as `HTTPSPolicyCallbackData`) size, `dwAuthType = AUTHTYPE_SERVER`, `fdwChecks = 0`, and `pwszServerName` to the owned, null-terminated configured reference. Set `CERT_CHAIN_POLICY_PARA.cbSize`, `dwFlags = 0`, and `pvExtraPolicyPara` to that structure. Initialize `CERT_CHAIN_POLICY_STATUS.cbSize` and call `CertVerifyCertificateChainPolicy(CERT_CHAIN_POLICY_SSL, ...)`. Require **both** a `TRUE` API result **and `policyStatus.dwError == 0`**. `TRUE` alone means the policy was evaluated, not that the peer passed. Do not enable unknown-CA, wrong-name, wrong-usage, time, or revocation ignore flags. The SSL policy call **does not itself perform revocation checking**; step 6 is indispensable.[^sslpara][^policy]

9. **Open only after all gates pass.** Validate final SSPI confidentiality/stream requirements and negotiated TLS policy as well as certificate policy. Flush final handshake tokens, preserve extra encrypted data, then enter `VerifiedOpen`. Re-run the appropriate automatic/custom verification gate after reauthentication/post-handshake processing before resuming application traffic. Any missing certificate, API failure, status error, unsupported identity check, deadline expiry, or trust-policy change prevents reuse.[^isc][^decrypt]

Microsoft's manual-validation checklist includes chain completeness/trusted anchor, validity for every certificate, revocation, path-depth constraints, correct usage, and contacted-server identity. Explicit chain construction, trust-status checks, strong-signature policy, and SSL server policy are necessary to satisfy it. **The mere presence of these API names in code does not prove equivalence** with the supported OS's automatic Schannel algorithm/distrust/enterprise policies; that remains a review and integration-test gate.[^manual][^chainpara][^policy]

### DNS and IP identity: retain a qualification gate

Use the **configured authority**, not the selected socket address for a DNS endpoint, reverse DNS, a name extracted from the certificate, an entire URL, or a host-with-port. Retain a normalized DNS reference consistently for SSPI/SNI and SSL policy. Reject embedded NUL/malformed authority input before passing C strings. Microsoft documents case-insensitive exact and wildcard-label/Punycode processing for `pwszServerName`; do not invent an extra permissive name matcher.[^isc][^sslpara]

For literal IPs, preserve the literal reference (without URL brackets/port) for policy verification and require an appropriate **IP SAN**, not a DNS SAN containing digits or a numeric common name. However, the retrieved Microsoft `SSL_EXTRA_CERT_CHAIN_POLICY_PARA` contract documents DNS/common-name matching and **does not precisely establish IPv4/IPv6 SAN matching behavior on every supported OS**. Do not claim that simply supplying an IP string proves the IP-SAN requirement. curl's maintained custom-trust path separately parses IP literals and compares binary `CERT_ALT_NAME_IP_ADDRESS` SAN entries; it does not use `CERT_CHAIN_POLICY_SSL` for its name check.[^sslpara][^altnames][^curl-verify]

Consequently, either qualify the OS SSL-policy path with positive/negative IPv4 and IPv6 fixtures and enforce the IP-SAN requirement with a reviewed additional strict SAN check, or report IP identity as unsupported. An additional check can use Windows certificate-extension decoding and exact address-byte comparison; it must **tighten**, not replace or override, a failing SSL-policy result. Malformed SAN, absent IP SAN, wrong address, or unsupported matching must fail before application data. Never recover by setting a name-ignore flag or substituting `localhost` for a configured IP. A correct IP SAN that the OS policy still rejects is a capability/interoperability gap, not permission to bypass policy.[^altnames][^decode][^policy]

### Unknown/offline revocation is a deliberate hard failure here

The current Microsoft `CertGetCertificateChain` page recommends end-certificate-only revocation with network retrieval and ignoring offline/unknown status for general TLS clients. That recommendation is **not** the stricter CanaryMiner contract requested for this investigation. This note deliberately requires chain-excluding-root checks and rejects unknown/offline status; it does not claim Microsoft mandates that availability tradeoff. Missing CDP/OCSP evidence, offline retrieval, stale CRL, or a weakly signed status object can therefore prevent an otherwise cryptographically valid private chain from opening. A plain private CA/leaf pair with no usable revocation evidence is not automatically a positive fixture. Do not add `CERT_CHAIN_POLICY_IGNORE_ALL_REV_UNKNOWN_FLAGS`, `SCH_CRED_IGNORE_NO_REVOCATION_CHECK`, `SCH_CRED_IGNORE_REVOCATION_OFFLINE`, or a curl-style best-effort mask to fix it.[^getchain][^chainpara][^credentials][^curl-verify]

## 4. Ownership and lifetime requirements

Use distinct RAII types, matched to the actual allocation family. The following lifetimes apply on every success, error, cancellation, and revalidation path:

* **Owned memory `HCERTSTORE`:** each successful `CertOpenStore`/`CertDuplicateStore` needs one `CertCloseStore`. Keep anchor/support stores alive and immutable for the engine's full use. The engine configuration API does not promise ownership transfer of the caller's handles; do not assume it closes them. Release chain contexts, then the engine, then caller-owned stores. This conservative ordering avoids relying on undocumented early-close behavior.[^open][^close][^create][^freeengine]
* **Added certificates:** `CertAddEncodedCertificateToStore` copies encoded bytes. A non-null returned `ppCertContext` is an owned reference requiring `CertFreeCertificateContext`; passing `NULL` avoids requesting that extra reference. Do not leak enumeration/search references when validating the bundle.[^add][^close]
* **Remote `PCCERT_CONTEXT`:** `SECPKG_ATTR_REMOTE_CERT_CONTEXT` requires `CertFreeCertificateContext`, **not `FreeContextBuffer`**. Treat its `hCertStore` as borrowed supporting input for the context's lifetime; do not separately close that handle as though `CertOpenStore` returned it. Explicitly duplicate a store if separate ownership is needed. Certificate/encoded-data pointers inside a context are not independently owned buffers.[^query][^close]
* **`PCCERT_CHAIN_CONTEXT`:** a successful `CertGetCertificateChain` result needs `CertFreeCertificateChain`. Its child chain/element pointers are borrowed from the chain context; do not free them individually. Keep the context live through all policy/diagnostic reads.[^getchain][^policy]
* **Parameter storage:** keep the configured wide name, usage OID array/string, strong-signature parameters, policy structures, and any store-handle array alive through their calls. The synchronous APIs' pointer parameters are not permission to retain pointers to temporary conversion buffers.[^chainpara][^sslpara][^engine]
* **SSPI context/credentials:** once created, release even a partially negotiated context with `DeleteSecurityContext`; then release its credentials using `FreeCredentialsHandle`, after all associated contexts are gone. Do not free either while a validation/handshake worker still uses it.[^isc][^freecred]
* **SSPI-allocated output tokens/alerts:** `ISC_REQ_ALLOCATE_MEMORY` allocations use `FreeContextBuffer`. Keep them until their bytes have been copied to owned pending-output storage or fully sent. For manually decoded certificate extensions, use the allocation/deallocation family selected by `CryptDecodeObjectEx`; its default allocated output uses `LocalFree`, not an SSPI or certificate free function. With `CRYPT_DECODE_NOCOPY_FLAG`, decoded pointers can reference the original encoding, which must remain alive until the decoded structure is freed. A caller's initial output-size value does not cap allocations when `CRYPT_DECODE_ALLOC_FLAG` is used; enforce fixture/input/allocation bounds separately.[^isc][^decode]

Avoid `CERT_CLOSE_STORE_FORCE_FLAG`: it invalidates outstanding contexts and is inappropriate after passing a store/context to other APIs. `CERT_CLOSE_STORE_CHECK_FLAG` is useful for fixture leak diagnostics, but **the store is closed even when it returns `FALSE` for pending references**; do not close it again. Cancellation must not destroy buffers/handles still used by a synchronous OS call.[^close]

## 5. No automatic client-certificate disclosure, including retry

For **both** modes, keep `SCH_CRED_NO_DEFAULT_CREDS`, empty client credentials, and `ISC_REQ_USE_SUPPLIED_CREDS` on the initial handshake and every continuation/re-entry. Do not set `SCH_CRED_USE_DEFAULT_CREDS`, enumerate the user's personal store, prompt for a certificate, or acquire replacement identity-bearing credentials. Microsoft explicitly warns that otherwise Schannel can locate and send a client certificate without notifying the application.[^credentials][^isc][^auth]

`SEC_I_INCOMPLETE_CREDENTIALS` means the peer requested a client certificate; it is not a reason to relax the flags. **Safest initial behavior:** fail with a distinct unsupported-client-authentication error, including during renegotiation. curl corroborates attempting continuation without a certificate when it first adds `ISC_REQ_USE_SUPPLIED_CREDS`, but that is not a general retry recipe for a client that already set the flag. If optional-certificate continuation is later required, qualify a bounded no-certificate continuation separately and reject repeated incomplete-credential states; never switch to automatic certificate selection.[^isc][^auth][^curl-io]

## 6. Auxiliary egress and native blocking limits

Connecting a socket only to loopback does **not** by itself make certificate validation local. Chain building can retrieve AIA issuers, CRLs/OCSP, CTLs, and platform roots. These URLs can come from a certificate, independent of the miner's endpoint/proxy allowlist. An exclusive anchor store is not a network sandbox.[^getchain][^engine]

For future **no-egress fixtures**, use all relevant controls on the explicit chain path: `CERT_CHAIN_DISABLE_AIA`, `CERT_CHAIN_CACHE_ONLY_URL_RETRIEVAL`, `CERT_CHAIN_DISABLE_AUTH_ROOT_AUTO_UPDATE`, and **separately** `CERT_CHAIN_REVOCATION_CHECK_CACHE_ONLY`, while retaining `CERT_CHAIN_REVOCATION_CHECK_CHAIN_EXCLUDE_ROOT`. The general cache-only flag explicitly does not cover revocation. Supply complete test intermediates and valid test-owned CRLs in memory where applicable, avoid external AIA/CDP/OCSP URLs, and require unknown status to fail. Cache-only checks can still consume ambient caches; they are not proof of hermeticity or evidence of freshly retrieved revocation status. Do not flush/populate machine caches as a workaround.[^getchain][^engine]

For normal automatic mode, `SCH_CRED_CACHE_ONLY_URL_RETRIEVAL_ON_CREATE` is documented for validation during **`AcquireCredentialsHandle`**, not as a universal no-network switch for subsequent server validation. Do not claim it contains all automatic Schannel egress. A local untrusted-certificate rejection test can still provoke auxiliary work; do not run native auto-mode integration under a zero-egress requirement unless an already-approved isolation policy actually contains it.[^credentials][^getchain]

In a future network-enabled custom mode, `CERT_CHAIN_REVOCATION_ACCUMULATIVE_TIMEOUT` with `CERT_CHAIN_PARA.dwUrlRetrievalTimeout` bounds cumulative revocation URL waits; the engine also has a URL timeout. Neither cited function offers a cancellable nonblocking socket-style interface or establishes a complete end-to-end bound covering all chain/AIA/cache/policy work. Do not execute potentially blocking native validation on the mining/job-intake thread, equate the URL timeout with the transport deadline, kill a thread inside Crypt32, or free its resources on cancellation. An owned worker must finish safely while a cancelled result is discarded; that alone does not guarantee bounded process shutdown. Hard shutdown/egress guarantees require separately qualified isolation or a deliberately restricted validation policy and may remain a release blocker. No firewall/global OS policy changes are proposed for this operator session.[^getchain][^chainpara][^engine]

## 7. Schannel byte-stream invariants independent of trust mode

* **Final output:** `InitializeSecurityContext` can return a nonempty `SECBUFFER_TOKEN` with `SEC_E_OK`; it must still be sent. Track “handshake locally complete,” “peer verified,” and “all required output flushed” separately. A partial socket send advances only the token's output offset; never repeat a successful SSPI call to regenerate it. Empty continuation tokens are legal. Inspect returned final security attributes, not merely requested flags.[^isc]
* **Incomplete/excess input:** preserve all unconsumed bytes on `SEC_E_INCOMPLETE_MESSAGE`; `SECBUFFER_MISSING.cbBuffer` is only a hint. Check all appropriate returned descriptors for `SECBUFFER_EXTRA`, validate lengths against owned input, retain the unprocessed tail, and process already-buffered work before waiting for another read event. The extra descriptor does **not** own a copy of the data. Preserve extra bytes when transitioning from handshake to record decryption as well.[^isc][^extra]
* **Post-handshake control:** `SEC_I_RENEGOTIATE` is also used for post-handshake TLS protocol messages, not just old renegotiation. Suspend application encryption/decryption, pass the buffer as modified by `DecryptMessage` to `InitializeSecurityContext` with `SECBUFFER_TOKEN`, and resume the handshake loop. Microsoft says an extra buffer is **not always present**; do not condition handling on `SECBUFFER_EXTRA` alone. Flush output and reapply the same trust/reference/client-identity gates before reopening. Bound work/deadlines; a failure remains a security failure.[^decrypt]
* **Records:** query `SECPKG_ATTR_STREAM_SIZES`, cap plaintext to `cbMaximumMessage`, allocate bounded header/data/trailer storage, and use the actual returned lengths. `EncryptMessage` encrypts in place and advances TLS state; it does not write a socket. **Encrypt each record once**, retain the generated ciphertext and send offset across would-block/partial sends, and flush it before encrypting the next record. Backpressure cannot cause re-encryption of the same accepted plaintext. Local consumption/ciphertext flush is not a peer application acknowledgement.[^encrypt][^curl-io]
* **Receive/lifetime:** successful decryption with no application bytes is legal, not EOF. Keep plaintext views alive until copied/consumed before compacting encrypted storage. Serialize the adapter's state, including validation and rehandshake ownership; no concurrent `InitializeSecurityContext` calls on one context. Do not busy-loop on incomplete/control-only buffers.[^decrypt][^isc][^extra]

curl corroborates final-token handling, manual verification before opening, and single record encryption, but its inspected handshake path expressly does **not** implement partial save/resume token sends, and its record send path waits to send the entire record or fail. Do not copy those scheduling choices as proof that CanaryMiner's strictly bounded nonblocking requirements have been met.[^curl-io]

## 8. Proposed safe fixture coverage, not executed results

Keep fixtures synthetic, test-owned, bounded, and loopback-only; use no real pool, account, device, private config, personal certificate, root install, or system-store write. Do not create a user/VM or alter firewall/root policy for these tests. Bind explicitly to loopback rather than a wildcard address; fixture DNS names can be verified against a preselected loopback socket without hosts-file edits or public resolution. Do not let this test-only socket/reference separation become a production name-verification override.

1. **Offline API tests:** build exclusive memory stores/engines and directly exercise the chain + SSL-policy acceptance gate without a TLS socket. Cover configured DNS mismatch, untrusted/wrong/empty root set, incomplete chain, expired/not-yet-valid leaf, wrong EKU, bad signature/constraints, malformed SAN, IPv4/IPv6 mismatch, revoked/unknown/stale revocation, and policy-call failure. Assert the aggregate error and policy status, not only API booleans. Use controlled current-valid synthetic material; `pTime` does not rewind root trust or CRL freshness, so fixed historical time is not a complete integration-time solution.[^getchain][^policy]
2. **Private-trust positive integration, when separately authorized:** use a private self-signed CA plus distinct server-auth leaf, complete supporting chain, and a current signed test CRL supplied in a memory supporting store. Keep retrieval cache-only and make failure to obtain revocation evidence fatal. First qualify that the chosen Crypt32 configuration actually consumes those local revocation inputs; do not claim this unexecuted design guarantees success. Prove a chain rooted in an unrelated anchor cannot pass; separately qualify OS-root exclusion without importing or enumerating personal identity material.[^getchain][^engine]
3. **Self-signed root-as-leaf limitation:** a single self-signed server certificate explicitly selected as the anchor may make a convenient no-install loopback fixture, subject to its usage/name/constraint policy. With `CHAIN_EXCLUDE_ROOT`, that one certificate is also the root and **can leave no non-root certificate whose revocation is checked**. A successful result therefore does not demonstrate leaf revocation, issuer validation, intermediate constraints, or ordinary CA/leaf trust. It is explicit trust in that exact anchor, not acceptance of arbitrary self-signed peers. Do not weaken CA-role/SSL checks to force this fixture to pass; retain the distinct-CA/leaf/CRL case for those properties.[^engine][^getchain][^policy]
4. **Identity negatives:** use different certificates for `localhost`, `127.0.0.1`, and `::1`; test absent SAN, numeric DNS SAN/common name instead of IP SAN, wrong IP, and a correctly encoded IP SAN. Assert zero application bytes written/delivered on failure and a specific unsupported-identity result where the OS contract is not qualified. Keep the configured reference independent of whichever certificate would otherwise match.[^sslpara][^altnames]
5. **Native I/O scripts/local peer:** fragment/coalesce handshake and records; force final `SEC_E_OK` output, incomplete headers, extra encrypted bytes, zero-plaintext success, partial ciphertext writes, cancellation, and post-handshake control. Assert one encryption per record, byte-exact output, no loss/duplication, bounded operation counts, and repeat verification before application reopening. Request client authentication initially and post-handshake; assert no client identity is selected, even when `SEC_I_INCOMPLETE_CREDENTIALS` is returned.[^isc][^extra][^decrypt][^encrypt][^auth]
6. **Normal-mode evidence must remain separate:** mocks can assert normal automatic flags and rejection paths. A custom-memory-store success cannot prove an automatic Windows-root positive path, Windows revocation service behavior, OS servicing compatibility, or real native trust. With root installation and external TLS connections out of scope, native automatic-trust positive qualification remains **deferred**, not passed by documentation or a custom-trust fixture. Never switch normal mode to manual only to turn that deferred gate green.

## 9. Remaining release gates

* Confirm the supported Windows/SDK matrix and exact applicable strong-signature, explicit-distrust, enterprise-policy, resumption, and reauthentication behavior of the explicit chain + SSL-policy path. These docs establish supported building blocks, not complete automatic-policy equivalence.
* Qualify DNS normalization and IPv4/IPv6 IP-SAN handling; until then reject unsupported identities rather than suppressing name checks.
* Demonstrate current local CRL/chain inputs under strict offline policy. A CA/leaf without revocation data should fail; a root-as-leaf success is not a substitute.
* Demonstrate no unexpected auxiliary egress and acceptable shutdown/cancellation behavior under the actual execution/isolation policy. Socket nonblocking mode does not bound Crypt32.
* Keep the existing automatic-trust recommendation and its unexecuted qualification gates visible. This note changes neither implementation nor the execution plan.
