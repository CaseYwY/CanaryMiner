# Owned worker transport and opt-in child entry (P-11f)

M-GAME/M-SUPERVISOR; R-GAME-004/005/006 and R-SAFE-001/002; T-GAME/T-INTENT; D-67. This slice carries the [P-11e protocol](worker-control.md) over a separately owned native channel, supplies cancellable worker IO and a background process owner, and admits that channel in an explicit development build of the native child entry. The subsequent [P-11g bridge](game-worker-session.md) connects the lifetime game runtime through a default-empty supervisor factory; ordinary CLI binding remains absent.

## Private bootstrap and entropy

`WorkerIdentitySource` performs one bounded, cancellable `LocalTaskProcess` request for 1..257 independent OS-generated 128-bit keys. The helper binds its parent before asking for entropy; there is no clock/PID/device/pseudorandom fallback. Responses require exact length, lowercase nonzero keys and no duplicates; original generation order is preserved. Cancellation/failure yields no keys. A used source cannot start another flight; the background caller must retain an unresolved helper rather than reconstruct it. The future supervisor must retain one parent-session key for the explicit parent lifetime and provision a fresh separate key for each worker incarnation.

The child inherits a private control channel and parent reference. Only numeric handles/descriptors appear in internal `--worker-control-v1` arguments; keys and commands stay in the private stream. Windows uses two anonymous pipes, an explicit handle inheritance list, and a suspended child assigned to a single-process kill-on-job-close Job before resume. Adoption verifies local pipe ownership, nonblocking mode, a live query/synchronize-only parent handle and Job membership. Linux uses a local stream socketpair, `posix_spawn`, an owned process group, close-from actions and descriptor 3. Adoption checks peer PID/UID and current parent, installs `PDEATHSIG`, rechecks the parent and sets close-on-exec. Unsupported close-from/reaping policies refuse.

The first complete frame must be a live revision-1 Pause. Its binding is frozen on that already paired channel; the real worker must reach an empty/drained boundary before the initial Paused receipt exists. A CLI flag or matching key format alone grants no Run authority. This is local owned-process pairing, not a security boundary against arbitrary same-user code. The supervisor still must bind the exact selected worker and preserve the same session/guard across incarnations.

## Bounded transport and cancellation

Both ends use bounded synchronous polling: Windows `PIPE_NOWAIT` and Linux nonblocking reads / `MSG_DONTWAIT | MSG_NOSIGNAL` writes. Each control read accepts at most 4096 bytes / 16 frames; each sender holds one frame of at most 384 bytes. A short or zero-byte write retains the exact remainder and original deadline. It never replaces partial bytes, extends a lease at delivery, flushes a pipe synchronously or waits for the peer to consume data. The child IO loop checks cancellation, parent liveness and expiry while idle, with a 5-ms host sleep slice. The gate checks expiry independently on worker reads.

Receipts use the dedicated control stream; stdout/stderr cannot impersonate them. IO occurs outside the gate mutex, and boundary callbacks remain memory-only. First-frame timeout, invalid framing, binding/revision fault, clock fault or stalled receipt output removes eligibility. EOF/operator stop is terminal; `stop()` revokes before joining. Physical search/preparation/source operations still respond at their cooperative boundaries, not at a promised 5-ms physical deadline.

The Windows mode is synchronous nonblocking polling, not overlapped IO. Its behavior follows [SetNamedPipeHandleState](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-setnamedpipehandlestate) and [WriteFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-writefile). No named endpoint, loopback listener or environment-key handoff is introduced.

## Process ownership and background facade

`WorkerControlProcess` is single-use. Launch/termination belong to one background owner thread. Graceful stop closes the channel without claiming exit. Forced termination targets the owned Job/process group, then polls actual exit/reaping for a bounded interval. Timeout or lost reaping ownership retains resources; unresolved objects move to a process-wide worker quarantine when destroyed. At most 256 worker ownership reservations are permitted. New worker launches refuse while unresolved ownership is known, including before the old object is destroyed. A later exact exit observation may settle a timeout; Linux `ECHILD` is not exit proof and never causes a signal to a possibly reused PID. This registry covers this worker module, not every existing helper subsystem.

`WorkerProcessOwner` supplies memory-only snapshots, one queued command and bounded complete log lines to the control thread. Launch, pumping, graceful drain and forced reaping run on its fixed background thread. Queuing is not a receipt; it never renews commands or starts sessions. Callers still use the issuer and evidence-derived deadlines. Stop immediately revokes publication/admission; its background owner then closes the channel. Already in-flight delivery and current work remain cooperative.

The log queue retains at most 32 whole lines / 32768 bytes, with an 8192-byte line cap. Oversized lines are discarded in full through newline, and overflow is counted. Control frames never enter this queue; consumers must still redact before display. Receipt snapshots preserve original observation times and remain historical after revocation. Every terminal path revokes before publishing `done`, including invalid start, failed launch and unsolicited clean exit. Native channel closure/termination occurs outside the facade mutex. `done` means the background job finished; `reaped` is a distinct process observation. A failed launch with no child is not fabricated into a reaped child, and unresolved ownership overrides a simultaneous stop result.

## Native admission and remaining integration

`CANARY_ENABLE_WORKER_CONTROL_RUNTIME` defaults **OFF**. Ordinary builds refuse the internal flag. The development variant accepts it only for an ordinary untuned worker run; benchmark, research/evidence, asynchronous selectors, tuning, invalid/duplicate handles and unowned channels refuse. The real `miner.cu` entry proves initial empty/drained Pause **before device discovery**, then installs the same client in `RunOptions::workPause`. Its legacy stdin watcher is omitted for this controlled child. CPU host stubs verify Run handoff by trapping the first forbidden device call.

The [P-11g bridge](game-worker-session.md) supplies stable parent identity provisioning, lifetime game supervision, evidence-to-lease composition and result admission. It distinguishes EOF from actual exit and retains incomplete/malformed receipt faults even when a poll also sees exit. Ordinary startup still supplies no factory: native mode/target review, qualified safety, latency isolation, CLI binding and production packaging remain required. Both production release recipes explicitly configure and verify this development capability OFF.

Windows parent death is bound by the assigned Job; Linux parent death is verified after child adoption. A loader/entry stall before Linux installs `PDEATHSIG`, genuine uninterruptible kernel waits, hostile same-user handle manipulation and installed-binary/loader trust are not certified. Launch, thread scheduling and kernel calls are not hard real-time operations. The background owner isolates ordinary launch/IO latency; unresolved native operations must never be replaced to manufacture progress.

## Verification

CPU native tests cover paired channels, initial hold, receipt/quiescence separation, held renewal, Run/Pause/Run, terminal EOF, expiry, old/skipped revisions, foreign binding refusal, original-deadline pipe backpressure, idle reader cancellation and forced reaping of an unresponsive owned process. Entropy tests cover strict requests, one-shot admission, cancellation and 1/2/257-key responses without logging keys.

The actual shared run-loop fixture uses this process/client pair for complete-work reconciliation and fresh resume. CLI host variants verify default-off/refused modes, unowned-channel rejection, stop/expiry before setup and Run reaching only the inert device trap. The lifecycle test kills only its own CPU parent and observes owned-worker death before the five-second lease expires. Linux also consumes the actual child with a competing reaper and checks quarantine refusal before/after owner destruction.

Background-owner tests cover startup cancellation, no implicit renewal, bounded whole-line retention under output flood, terminal refusal and forced drain completion. Final review first reproduced missing terminal revocation on invalid start, failed native launch and unsolicited clean exit, then fixed all three through consistent terminal publication.

Windows/MSVC focused **10/10** passes. Windows/Linux native IPC/identity/owner tests pass **122** checks, including actual shared-loop subprocess and opt-in native CLI-stub paths. Lifecycle tests pass adopted-parent death before lease expiry and **9** native CLI refusals; Linux additionally passes lost-reaper quarantine. Linux **ASan+UBSan** passes the final **122** checks and lifecycle selection, rebuilding process/owner/tests and reusing unchanged instrumented protocol/identity/child fixtures. The earlier instrumented shared-loop suite passes **57** checks. Architecture/import, ordinary fixture-artifact and native-recipe checks pass; release recipes receive syntax checks only. Initial CLI fixtures omitted their required algorithm selector; this was corrected without weakening admission.

On-machine GPU/game integrated acceptance is deferred until planned implementation is ready; these are development CPU checks. Production CUDA/SASS, actual pool, installed helper/loader trust, physical pause and gameplay qualification remain open.
