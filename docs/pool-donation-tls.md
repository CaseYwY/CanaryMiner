# Independent strict donation transport

The user and donation lanes carry separate transport policies. The donation lane keeps the compiled F2Pool peer, account, worker, mainnet and donation scheduler. Its TLS route, if qualified for this build, requires a saved Strict TLS declaration for that exact donor host and port. The supervisor freezes the exact approved URL for worker restarts. A replacement worker must still find its matching strict donation declaration. A missing, changed or unrequested donation policy refuses startup before device setup. Each donation run selects the approved TLS endpoint, clears the user's plaintext fallback, and uses the existing native trust and hostname verification before sending protocol bytes.

**Production admission remains closed.** F2Pool's public Pearl address table still lists the existing TCP endpoint. Its Pearl tutorial labels the same-port SSL form as illustrative. The production build leaves the qualified donation port unset. A saved declaration or private worker flag cannot supply this capability. Legacy donation with a TCP user session and strict user TLS with donation off retain their existing behavior. [F2Pool address table](https://f2pool.zendesk.com/hc/en-us/articles/360058887912-Mining-pools-info-payout-schemes-and-thresholds-at-f2pool) · [F2Pool Pearl tutorial](https://f2pool.zendesk.com/hc/zh-cn/articles/59248379419417-PRL-Pearl-%E6%8C%96%E7%9F%BF%E6%95%99%E7%A8%8B)

Tests supply an internal fixture approval to check policy admission and donation lane handoff. An unsuccessful donation window uses the existing retry and debt accounting, and user work resumes with the original user policy. A real secure donation endpoint requires affirmative Pearl-specific evidence, trust and authentication validation for the fixed account, and independent release acceptance.
