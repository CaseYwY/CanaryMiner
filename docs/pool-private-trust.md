# Offline native Windows private-chain inspection (P-12c)

M-TLS; R-TLS-003/004; T-TLS/T-PRIVACY/T-RELEASE; D-94.

**Default-off development inspection, not a Schannel handshake, production custom-CA mode or mining permit.** `inspectPearlTlsPrivateTrust` can inspect an explicit synthetic DNS reference, leaf, exclusive self-signed CA anchors, intermediates and CRLs using actual Windows Crypt32 APIs. It never changes normal automatic Schannel trust, creates a connection, chooses a pool, installs a root, selects a client certificate/private key or writes a system certificate store. Ordinary miner activation remains absent.

The independently enabled Windows-only CMake option is `CANARY_ENABLE_POOL_TLS_PRIVATE_TRUST`. Other platforms/default builds return Unavailable for otherwise valid enabled input. Disabled input performs no native inspection. Input bounds and cancellation apply before native calls on all platforms: at most 16 objects per collection, 64 KiB per DER object, 512 KiB combined and a bounded ASCII DNS reference. Literal IPv4/IPv6 returns UnsupportedReference rather than substituting another name or claiming unqualified IP-SAN behavior.

## Native acceptance, not Boolean API success

All supplied material is copied into new nonpersistent **memory stores**. An anchor must explicitly have CA basic constraints, certificate-signing key usage, equal subject/issuer and a valid self-signature. Supporting certificates and CRLs are not promoted to anchors. A CA/root presented as the target leaf is refused, so root-as-leaf cannot produce a vacuous non-root revocation success. Malformed or missing anchors/material fail; no system-trust retry is permitted.

The inspection creates a nondefault chain engine with `hExclusiveRoot`, no peer trust, no exclusive-intermediate flag and **all restricted-store handles NULL**. Supporting objects are additional stores, not anchors. The Microsoft SDK explicitly forbids combining exclusive and restricted handles: the initial implementation reproduced `E_INVALIDARG` before chain evaluation, and the corrected configuration passes the actual fixture. The earlier research proposal is corrected in [the private-trust study](research/schannel-private-trust.md), retaining that evidence rather than treating a failed engine call as trust acceptance.

Engine/call flags prohibit AIA retrieval and automatic platform-root updates, require cache-only URL/revocation retrieval, and retain **chain-excluding-root revocation checks**. The requested usage is exactly server authentication. Native current strong-signature policy is supplied without disabling the end-key check; weak-signature checks are enabled. A chain-call success is not acceptance: every aggregate trust-error bit, including unknown/offline revocation and future unrecognized bits, refuses. Exact chain errors and a structured native stage/error remain distinct historical diagnostics.

Only an error-free nonempty chain proceeds to `CERT_CHAIN_POLICY_SSL` with `AUTHTYPE_SERVER`, the original owned DNS reference and **zero ignore flags**. Both API success and `dwError == 0` are required. SSL policy does not replace revocation. Cancellation is rechecked before chain evaluation, after it and before returning success. All contexts are freed in ownership order before their stores disappear.

## Isolation and lifetime limits

Exclusive anchors exclude the system Root/TrustedPeople stores **as trust sources**, not all public supporting-store/cache reads. The SDK's exclusive-mode supporting world can include CA/My stores and OS caches; this is not a hermetic certificate sandbox or proof of equivalence with normal automatic Schannel/enterprise/distrust policy. No application code enumerates identity stores or requests a private key. Fixture issuers/keys are newly generated and unrelated to ambient certificates.

No input fixture contains AIA/CDP/OCSP network URLs. The API retains explicit cache-only, no-AIA and no-root-update controls, but this suite is not process-wide network-egress instrumentation or proof about unrelated OS background services. Native Crypt32 calls remain synchronous and have no proven hard cancellation/shutdown deadline. Do not execute this inspector on an ordinary mining/job-intake/render thread or infer permission to kill a thread inside Crypt32. Future native ownership/isolation, revalidation after handshake/reauthentication, OS-version servicing and full automatic-policy equivalence remain release gates.

## Fixture and verification scope

`tests/make_tls_private_trust_fixture.py` explicitly generates public DER using a separately supplied Python `cryptography` installation. It downloads nothing, writes no private keys, uses exclusive file creation and requires a new test-owned output directory. Each scenario has a fresh unique synthetic issuer/key to avoid borrowing a previous scenario's revocation evidence. It is not imported/generated by default CTest and is not a runtime dependency. An explicitly supplied `CANARY_TLS_PRIVATE_TRUST_FIXTURE_DIR` can register the additional native fixture case when the Windows capability is enabled.

The real native fixture covers distinct CA/leaf plus a valid current signed CRL, missing/stale CRL, explicitly revoked leaf, expired/future leaf, wrong server usage, bad signature, wrong anchor, DNS mismatch, root-as-leaf and leaf-as-anchor. Negative cases assert the relevant native trust bits, not only an overall rejection; wrong-name refusal requires an otherwise clean chain and a failing SSL-policy result. Default-off/malformed/cancelled/unsupported-IP paths are separate. These observations do not qualify a Schannel record stream, private-trust production activation, native automatic-root positives, TLS endpoints, donation routing or physical/release behavior. Final results are recorded in the execution ledger.
